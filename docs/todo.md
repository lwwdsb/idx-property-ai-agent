## 三、已知缺陷（有明确修法，未修）

- [ ] **`approveAndSend` 是 check-then-act**：读状态 → 发 SMTP → 写状态，三步无原子性。
      两个并发 approve 会双发；发成功但写状态失败会在下次审批时重发。
      修法：`UPDATE ... WHERE id=? AND status='pending_approval'` 靠 affectedRows=1 拿唯一执行权（数据库层 CAS）
- [ ] **`/orchestrate` 幂等缓存挡不住真并发**：结果是执行完才写缓存，两个同时到达的请求都会执行。
      修法：singleflight —— map 里存正在进行的 Promise 而不是结果（Node 单线程让 get/set 之间天然是临界区）
- [ ] **`USC` 地标无确定性映射**：e2e 24/25 的那条断言回复含 "Los Angeles"，但代码里没有地标表，
      一直靠 LLM 主动说出城市。要么加一张小表（USC/UCLA/迪士尼 → 城市），要么改断言
- [ ] **`ORCH_TOKEN` 两边不通**：`openclaw-plugin/index.ts` 直接读 `process.env`，**不加载 `.env`**，
      而它跑在 launchd 启动的 gateway 进程里。所以只往 `.env` 加 token 会让 live WhatsApp 全部 401。
      要补就得两边一起（给 gateway 注入环境变量，或让插件也加载 `.env`）

## 记忆选择器：常驻偏好走错了通道（2026-09-27 发现）

`prefers-short-answers` 这类**全局回答风格偏好**目前是 `selectMemories` 的候选项之一，但它对每一个会产出回答的任务都成立，因此不携带任何 per-task 信息。实测后果是选择器把它挂到每个任务上（v2 的 4 次多选里有 3 次是它）；而一刀切禁掉它又会打破 `ms-002`（"什么是 DOM"）——那条用例的整个 gold 答案就是它，因为纯域内问答里风格是唯一能贡献的记忆。

所以它既不是"不相关"也不是"总相关"，而是**被支配的**：有实质性记忆时它一文不值，没有实质性记忆时它是唯一有价值的。现在的 prompt 规则 4 把这个写成了优先级排序，但**优先级排序不是相关性判断**——这正是它根本不该待在 per-task 选择器里的信号。

正确的去处是和结构化约束同一条通道：结构化约束已经通过声明式 `slots` + `seedFilterFor` 绕过选择器、作为常驻软默认注入。回答风格应该照做——变成一个常驻的响应格式默认值，而不是每轮花一次 LLM 判断去问"这次相关吗"。

做了之后：规则 4 可以整条删掉，选择器只判真正任务相关的记忆，`ms-002` 的 gold 要相应改成 `[]`（风格不再经由选择器），L2 的 precision/recall 都会变干净。

**动之前必须重复跑取带**（见 `eval/README.md` 的噪声带一节），不能拿单跑比单跑。
