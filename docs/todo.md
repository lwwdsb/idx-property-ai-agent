## 三、已知缺陷（有明确修法，未修）

- [ ] **`approveAndSend` 是 check-then-act**：读状态 → 发 SMTP → 写状态，三步无原子性。
      两个并发 approve 会双发；发成功但写状态失败会在下次审批时重发。
      修法：`UPDATE ... WHERE id=? AND status='pending_approval'` 靠 affectedRows=1 拿唯一执行权（数据库层 CAS）
- [ ] **`/orchestrate` 幂等缓存挡不住真并发**：结果是执行完才写缓存，两个同时到达的请求都会执行。
      修法：singleflight —— map 里存正在进行的 Promise 而不是结果（Node 单线程让 get/set 之间天然是临界区）
- [ ] **`USC` 地标无确定性映射**：e2e 24/25 的那条断言回复含 "Los Angeles"，但代码里没有地标表，
      一直靠 LLM 主动说出城市。要么加一张小表（USC/UCLA/迪士尼 → 城市），要么改断言
- [ ] **`ORCH_TOKEN` 两边不通**：`openclaw-plugin/index.ts` 直接读 `process.env`，**不加载 `.env`**，
      而它跑在 launchd 启动的 gateway 进程里。所以只往 `.env` 加 token 会让 live WhatsApp 全部 401。
      要补就得两边一起（给 gateway 注入环境变量，或让插件也加载 `.env`）

## 六、评测基础设施

- [ ] **graded 集 schema 修复**：`label.relevant` 只存正例 + 一个 `pool_size`，
      分不清"判过=0"和"没判过"，所以索引一变这个集就失效（实测 dense top-10 有 50% 落在集外）。
      要显式存池内 id 并记 0 分，且每次索引变化重新池化+重判
- [ ] **bad case 双池**：主集冻结做纵向对比，新增 case 进独立 regression pool 只做布尔断言。
      因为"把 bad case 加进评测集"和"对比前后指标"结构上互斥——尺子变了就没法比
- [ ] **调度**：两个 loop 都是手动跑的，没挂 cron，所以严格说不是"自"迭代。
      注意 launchd 读不了 Desktop 下的文件（TCC），要用终端里的 cron 或手动触发
